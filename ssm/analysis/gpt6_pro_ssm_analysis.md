# 판정: 현재 커밋을 “완전한 설계”로 승인할 수 없습니다

GitHub 커넥터로 `initguru/store-ssm-patcher`와 고정 커밋 **`1e0204fc54c16cee569c59f090d2275920ea12a4`**의 일치를 확인하고, 지정한 원격 파일 7개를 읽었습니다. 다른 브랜치나 별도 파일 번들로 대체하지 않았습니다. [검토한 커밋](https://github.com/initguru/store-ssm-patcher/commit/1e0204fc54c16cee569c59f090d2275920ea12a4)

**확인된 정적 근거만으로도 완전성 주장에는 반례가 있습니다.** 정책 상태를 바꾸는 호출과 관련 부수 동작이 일관되게 처리되지 않고, 검증기는 실제로 보장하는 범위보다 좁으며, 테스트와 REA 산출물을 이 커밋의 실행 결과에 연결하는 근거도 부족합니다.

다만 요청 중 **단말 보안 정책을 강제로 해제하면서 서명·무결성·환경 검사에서 그 변경을 숨기는 구체적인 바이트 패치, 추가 우회 지점, 자동 우회 규칙 집합**은 제공할 수 없습니다. 아래는 원격 근거에 따른 상태 일관성, 검증 신뢰성, 증거 완전성 및 일반적인 버전 대응 아키텍처의 검토입니다.

| 질문 | 현재 판정 |
|---|---|
| 순정 APK 대비 비정상 호출·트래픽·탐지 편차가 모두 제거되었는가? | **입증되지 않았습니다.** 게시된 정적 분석과 테스트에는 전체 실행 경로·트래픽·서버 관측의 동등성을 확인할 증거가 없습니다. |
| 기존 제한 정책의 상태 전환과 동의·서버 보고 보존이 완전한가? | **완전하지 않습니다.** 캡처 상태 변경 호출 제거와 소유자 관련 동작 잔존이 함께 나타나며, 동의·정책 적용·서버 반영을 구분한 검증이 없습니다. |
| 앞으로 모든 버전을 코드 수정 없이 처리하는 Universal Patcher인가? | **현재 구현은 아닙니다.** 일부 네이티브 동적 탐색은 존재하지만, 고정 위치·특정 빌드·외부 작업 디렉터리에 대한 의존이 남습니다. 임의의 미래 버전까지 100% 자동 처리한다는 보장도 성립하지 않습니다. |

## 1. 먼저 확정해야 할 증거의 범위

### 패치 목록과 분석 목록은 일치합니다

원격 `patch_ssm.py`의 패치 튜플을 분석 JSON의 `patch_tuples`와 대조한 결과는 다음과 같습니다.

| 구분 | patcher의 패치 위치 수 | 분석 JSON의 패치 위치 수 | 목록 일치 |
|---|---:|---:|---|
| `classes.dex` | 38 | 38 | 일치 |
| `classes2.dex` | 4 | 4 | 일치 |
| 합계 | 42 | 42 | 일치 |

다만 **패치 위치 42개와 패치된 메서드 42개는 다른 수치**입니다. 분석에 수록된 메서드는 42개이고, 그중 `has_patch=true`는 37개입니다. 나머지 5개는 비교에 필요한 미변경 메서드입니다. 네이티브 분석에는 arm64 6곳, 나머지 ABI 각각 5곳으로 총 21개의 변경 창이 수록되어 있습니다. [SSM 패치 목록](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/patcher/patch_ssm.py#L13-L52) · [바이트코드·네이티브 분석](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/analysis/ssm_patched_and_core_methods.json)

이 일치는 **게시된 계획과 게시된 분석의 일관성**을 확인합니다. 다음 사항까지 증명하지는 않습니다.

- 분석 JSON이 원본 APK 전체를 빠짐없이 표현한다는 것.
- 변경 후 DEX 전체가 Android 검증기를 통과한다는 것.
- 모든 ABI의 네이티브 함수가 실행 시 안전하다는 것.
- 기존 정책이 적용된 단말에서 원하는 상태 전환이 실제로 일어난다는 것.
- UI 표시, 로컬 상태, 서버 보고, 서버 저장 상태가 일치한다는 것.

이번 검토에서는 사용자 제약에 따라 APK 실행·테스트 실행·로컬 파일 접근을 하지 않았습니다. 따라서 **42개 패치 모두의 실행 안전성을 검증했다는 판정은 하지 않습니다.**

## 2. 정책 상태와 관련해 확인된 문제

### F-01 — 요청에 적힌 메서드의 기능 대응부터 수정해야 합니다

고정 커밋의 디스어셈블리에서 확인되는 대응은 다음과 같습니다.

| 메서드 | 게시된 문자열·호출에서 확인되는 기능 |
|---|---|
| `u0(Z)V` | 화면 캡처 상태 |
| `x0(Z)V` | USB 상태: `setUsbState`, `setUsbDisabled` |
| `d0(Z)V` | 개발자 모드 상태: `setDeveloperMode`, `setDeveloperModeDisabled` |

따라서 요청의 **“`x0`는 카메라, `d0`는 USB”라는 대응은 이 커밋의 근거와 일치하지 않습니다.** 이 대응을 전제로 세 기능의 일관성을 설계하거나 테스트하면, 실제로 다른 정책을 확인하면서 카메라까지 검증했다고 오판할 수 있습니다. [개발자 모드 메서드](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/analysis/ssm_patched_and_core_methods.json#L8357) · [USB 메서드](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/analysis/ssm_patched_and_core_methods.json#L9375)

메서드명은 난독화된 식별자이므로, 기능의 정본은 이름이 아니라 **실제 호출 대상과 데이터 흐름**이어야 합니다.

### F-02 — `u0`의 현재 변경은 상태 전환의 완전성을 보장하지 않습니다

게시된 `u0`에는 다음 사항이 함께 존재합니다.

1. 세 곳의 화면 캡처 상태 설정 호출이 제거되어 있습니다.
2. 현재 상태와 입력을 비교하여 반환하는 분기는 남아 있습니다.
3. `clearProfileOwner`와 `setProfileOwner` 호출은 남아 있습니다.
4. 소유자 관련 호출에는 SDK 버전과 입력·상태에 따른 조건이 있습니다.

따라서 **“캡처 정책 관련 동작이 모두 사라졌다”는 해석은 틀립니다.** 반대로, **“남은 소유자 호출이 모든 단말에서 항상 실행된다”는 해석도 틀립니다.** 해당 호출은 조건부로 도달할 수 있는 상태로 남아 있습니다. 게시된 코드에서는 SDK 24와 비교하는 분기가 이 경로를 제한합니다. [현재 `u0` 전체 기록](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/analysis/ssm_patched_and_core_methods.json#L8854)

핵심 문제는 **“추가 제한을 설정하지 않는다”와 “이미 존재하는 제한을 해제한다”가 서로 다른 동작**이라는 점입니다. 상태 설정 호출을 없앤 사실만으로는 기존 OS 정책의 해제를 입증할 수 없습니다. 다른 관리 주체나 다른 실행 경로가 상태를 바꾸지 않는다면 기존 제한이 남을 가능성을 배제할 수 없습니다.

또한 정책 설정과 소유자 변경은 서로 다른 책임입니다. 현재 변경은 한쪽 호출을 제거하면서 다른 쪽의 실행 가능성을 남깁니다. 따라서 상태 전환이 실패하거나 생략된 뒤에도 관련 부수 동작이 발생하지 않는다는 보장이 없습니다.

#### 상태가 같으면 반환하는 분기는 별도로 판단해야 합니다

`C()Z`의 게시된 흐름은 캡처 제한 여부를 읽고, 이를 허용 상태의 의미로 변환하는 형태입니다. `u0`는 그 결과와 입력을 비교합니다. [상태 조회 메서드](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/analysis/ssm_patched_and_core_methods.json#L7772)

여기서 두 요구를 구분해야 합니다.

- **목표 상태가 실제로 성립하도록 한다.**
- **매번 setter를 반드시 호출한다.**

신뢰할 수 있는 조회 결과가 이미 목표 상태라면, setter를 생략하는 것은 일반적인 멱등 처리입니다. 따라서 동일 상태 분기가 존재한다는 사실만으로 결함이라고 할 수는 없습니다. 결함 여부는 조회 값이 실제 적용 상태를 정확히 나타내는지, 다른 정책 주체의 영향이 있는지, 실패 후 상태를 다시 관측하는지에 달려 있습니다.

현재 근거로 확정할 수 있는 문제는 **“설정 호출 제거만으로 기존 정책의 정상적인 상태 전환까지 보장할 수 없다”**는 것입니다.

### F-03 — 동의 보존과 정책 적용 성공을 구분한 계약이 없습니다

`"출입정책 사용 동의"`가 보존되었다고 판단하려면 최소한 다음을 각각 확인해야 합니다.

| 대상 | 확인해야 하는 내용 |
|---|---|
| 사용자 선택 | 실제 동의·거부 선택이 유지되는가 |
| UI 상태 | 화면이 그 선택과 처리 결과를 정확히 표시하는가 |
| 로컬 저장 | 재실행 후에도 올바른 값이 복원되는가 |
| 정책 적용 | OS 또는 관리 서비스가 요청을 실제로 적용했는가 |
| 서버 요청 | 동의와 적용 결과가 각각 올바르게 전달되는가 |
| 서버 저장 | 서버가 수신한 상태를 어떤 의미로 저장했는가 |

**동의는 정책 적용 성공의 증거가 아닙니다.** 동의한 사용자의 정책 적용이 실패할 수도 있고, 관리자가 정책을 정상적으로 변경해도 기존 동의 기록은 유지될 수 있습니다.

현재 테스트는 이 구분을 검증하지 않습니다. 바이트가 기대한 값인지 확인하는 테스트에서, 동의 화면의 상호작용·저장 상태·서버 확인 응답까지 보존되었다는 결론을 낼 수 없습니다. [SSM 테스트 전체](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/patcher/test_patch_ssm.py)

올바른 상태 모델에서는 적용 실패나 미확인 상태가 성공으로 대체되지 않아야 합니다. 서버에 전달하는 결과 역시 실제 동의와 실제 적용 결과를 구분해야 합니다.

## 3. 바이트코드 검증기의 보장 범위가 부족합니다

### F-04 — `validate_methods()`는 타입·제어 흐름 검증기가 아닙니다

SSM은 Store의 `validate_methods()`를 재사용합니다. 이 함수가 실제로 검사하는 항목은 대략 다음과 같습니다.

- 지원하는 opcode인지.
- 명령어 폭에 따라 메서드 끝까지 읽을 수 있는지.
- 일부 `move-result` 앞에 허용된 명령이 있는지.
- 레지스터 번호와 일부 wide register 쌍이 범위 안에 있는지.
- `try_item`의 시작과 끝이 명령어 경계에 해당하는지.

이는 유용한 구조 검사이지만, 요청한 안전성 검증 전체를 대체하지는 못합니다. [공유 검증기 구현](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/store/patcher/patch_store.py#L103-L162)

| 요청한 안전성 | 현재 구현에서 확인되지 않는 부분 |
|---|---|
| 레지스터 타입 오염 | 경로별 타입 전파, 합류 지점의 타입 병합, 참조·정수 구분 |
| 정상적인 호출 | receiver 타입, 인자 타입·개수와 프로토타입의 일치 |
| 정상적인 반환 | 메서드 반환형과 반환 opcode·값의 관계 |
| 분기 안전성 | 모든 분기 대상이 유효한 명령 시작점인지 |
| 예외 처리 안전성 | catch handler 목록 해석, handler 진입점·예외 타입 검증 |
| 도달 가능성 | 변경 후 CFG와 예외 간선에 따른 실제 도달 경로 |
| 동기화 안전성 | monitor 획득·해제와 조기 반환의 관계 |
| 런타임 수용성 | Android 플랫폼 검증기와 실제 클래스 로딩 결과 |

특히 현재 구현은 `try_item`에서 읽은 `handler_off`를 사용해 catch handler 내용을 검증하지 않습니다. **try 구간의 숫자가 명령 경계에 맞는다는 것과 예외 처리 그래프가 유효하다는 것은 다른 보장**입니다.

분석 JSON도 메서드별 `tries`에 시작·끝·`handler_off`를 기록하지만, 이것만으로 전체 handler 타입과 진입 관계를 복원한 검증 결과라고 볼 수 없습니다. [메서드 분석 구조](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/analysis/ssm_patched_and_core_methods.json)

따라서 현재 상태를 다음처럼 표현하는 것이 정확합니다.

> 패치 목록과 제한적인 구조 검사의 일관성은 확인할 수 있지만, 레지스터 타입·예외 경로·런타임 부작용이 모두 안전하다는 인증은 없다.

이는 **실제로 모든 패치에 타입 오류가 있다는 주장도 아닙니다.** 현재 검증으로 그런 오류의 부재를 증명하지 못한다는 판정입니다.

### F-05 — 변경 후 명령어를 독립적으로 해석한 결과와 원본 주석을 구분해야 합니다

분석 JSON의 명령어 항목은 `orig_hex`, `patched_hex`, `changed`, `opcode`, `ref`를 함께 갖습니다. 변경된 항목에서도 `opcode`와 `ref`는 원래 호출이나 참조를 나타내는 경우가 있습니다.

예를 들어 호출 바이트가 제거된 항목에 원래 호출 대상 `ref`가 남아 있다는 이유만으로, 변경 후에도 그 호출이 실행된다고 판단하면 안 됩니다. 반대로 원본 명령어 단위로 나눈 항목에 변경 바이트가 들어 있다는 사실만으로, 변경 후 명령 경계가 독립적으로 검증되었다고 볼 수도 없습니다. [분석 JSON의 명령어 항목](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/analysis/ssm_patched_and_core_methods.json)

검토 자료에는 **원본 명령어 설명, 변경 바이트, 변경 후 재해석 결과**가 명확하게 구분되어야 합니다.

## 4. 테스트와 산출물의 출처 연결에 문제가 있습니다

### F-06 — 게시된 저장소 배치와 실행 의존 경로가 맞지 않습니다

SSM의 공유 검증기 로드는 다음 위치를 기대합니다.

- `patch_ssm.py`와 같은 디렉터리에 있는 `patch_store.py`.

하지만 고정 커밋에서 실제 파일은 각각 다음 위치에 있습니다.

- `ssm/patcher/patch_ssm.py`
- `store/patcher/patch_store.py`

서명 처리도 같은 디렉터리의 Store 모듈을 다시 불러옵니다. 원격 트리에는 SSM 디렉터리의 해당 형제 파일이 없습니다. 따라서 **게시된 저장소 배치 그대로 독립 실행 가능하다고 볼 수 없습니다.** 별도 복사나 배치 단계가 있다면 그 단계가 실행 계약에 포함되어야 하는데, 지정된 코드에는 그 연결이 없습니다. [검증기 로드](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/patcher/patch_ssm.py#L55-L59) · [서명 의존성 로드](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/patcher/patch_ssm.py#L209-L221) · [고정 커밋의 파일 배치](https://github.com/initguru/store-ssm-patcher/tree/1e0204fc54c16cee569c59f090d2275920ea12a4)

또한 SSM 실행은 입력 DEX를 `/tmp/ssm_re_work/ssm`의 추출 파일과 비교합니다. Store 역시 별도 작업 디렉터리의 원본 DEX에 의존합니다. 이 비교는 해당 작업 환경에서 원본 혼동을 막는 데 도움을 줄 수 있지만, **입력 APK만 받아 자체적으로 처리하는 범용 실행 계약은 아닙니다.** [SSM 입력 의존성](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/patcher/patch_ssm.py#L179-L195) · [Store 입력 의존성](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/store/patcher/patch_store.py#L232-L242)

### F-07 — 테스트가 이 커밋의 모듈과 새 산출물을 직접 검증하지 않습니다

`test_patch_ssm.py`는 저장소 안의 인접 모듈을 가져오는 대신 `/tmp/ssm_re_work/patch_ssm.py`를 가져옵니다. 원본과 patched APK도 특정 사용자 디렉터리의 기존 파일을 읽습니다. [테스트의 import 경로](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/patcher/test_patch_ssm.py#L6-L10) · [기존 APK fixture 의존](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/patcher/test_patch_ssm.py#L45-L61)

그 결과 테스트가 통과하더라도, 그 사실만으로 다음 연결이 성립하지 않습니다.

> 이 커밋의 코드 → 이 입력 APK → 이번 실행에서 생성한 출력 APK → 해당 출력에 대한 검증

이것은 mock만 사용하는 테스트는 아닙니다. 실제 APK를 읽는 부분이 있습니다. 문제는 **코드와 산출물의 출처·시점 연결**입니다.

또한 예상 튜플이 패치 목록에 있는지, 기존 patched APK에 그 바이트가 있는지를 확인하는 테스트는 구현 계약을 확인합니다. 사용자에게 필요한 정책 상태·동의·서버 보고라는 행동 계약은 별도로 검증해야 합니다.

### F-08 — SSM의 DEX 검사는 예상 밖 변경을 전체 범위에서 배제하지 않습니다

SSM의 `check()`는 DEX 체크섬과 알려진 패치 위치를 확인하지만, 해당 DEX의 나머지 바이트 전체가 예상 결과와 같은지 비교하지 않습니다. 반면 같은 함수의 네이티브 처리와 Store의 DEX 검증에는 원본에 허용된 변경을 적용한 전체 예상 바이트와 비교하는 과정이 있습니다. [SSM 출력 검사](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/patcher/patch_ssm.py#L141-L166) · [Store DEX 전체 비교](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/store/patcher/patch_store.py#L199-L212)

따라서 SSM의 현재 검사를 **“알려진 위치 외에는 아무 변경도 없다”는 증거**로 사용할 수 없습니다. 체크섬이 맞는다는 사실은 파일 내부의 자체 일관성을 보여줄 뿐, 허용된 변경만 존재한다는 의미는 아닙니다.

## 5. REA 번들이 증명하는 것과 증명하지 않는 것

REA 파일은 최초 파일 조회에서 본문이 비어 반환되어, 고정 커밋 트리에 연결된 **동일 파일의 Git blob**을 직접 조회해 읽었습니다. 별도 번들로 대체하지 않았습니다.

### 런타임 관측 자료가 없습니다

번들에는 다음 상태가 기록되어 있습니다.

- `captures`: 0개
- `environments`: 0개
- `scenarios`: 0개
- SSM 서명 검사 레코드의 `runtime_execution`: `not-performed`

서명 검사 자체도 구조 검사이며, 암호학적 서명 검증과 Android 실행을 수행하지 않았다는 제한을 명시합니다. [REA 증거 번들](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/rea/rea_ssm_evidence.json)

따라서 번들의 `self_consistent=true` 등을 다음 주장으로 확대하면 안 됩니다.

- Android 설치·로딩이 검증되었다.
- 실제 정책이 변경되었다.
- 백그라운드 감시의 모든 경로가 검증되었다.
- 순정과 동일한 네트워크 관측 결과를 얻었다.
- 서버가 동일하게 판정했다.

Patcher도 출력 문구에서 Android 플랫폼 검증기를 실행하지 않았다고 명시합니다. 이 한계 표시는 적절하지만, 그 문구가 실행 증거를 대신하지는 않습니다. [SSM의 실행 범위 표시](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/patcher/patch_ssm.py#L222-L232)

### 같은 patched APK 이름에 서로 다른 산출물이 있습니다

번들에는 `SSM_5.5.14.2624_patched.apk`라는 같은 이름으로 적어도 다음 두 SHA-256 산출물이 기록되어 있습니다.

| 구분 | SHA-256 |
|---|---|
| 산출물 A | `257a374d42eb07499a2d96e9540307d27f7a82b0b2348d5f9ededadfde825fae` |
| 산출물 B | `5978b6bc5d9e338e623d955e3c0b1a30c385e10fbbf3dfd04dfc5139486c7dc8` |

여러 실험 산출물을 보관하는 것 자체는 문제가 아닙니다. 문제는 **이 커밋의 patcher가 어느 산출물을 생성했는지, 그 산출물에 어떤 실행 검증을 수행했는지를 확정할 연결이 부족하다는 것**입니다. 파일명이나 배열 순서만으로 최신·정본을 선택해서는 안 됩니다. [REA의 산출물별 기록](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/rea/rea_ssm_evidence.json)

## 6. 서명·무결성·백그라운드 감시의 “완전성”은 입증되지 않았습니다

`ssm_callgraph_and_signatures.json`은 42개 메서드의 문자열·호출·필드 요약을 제공합니다. 하지만 파일 구조에는 애플리케이션 전체의 완전한 역방향 caller 목록이나, 모든 실행 경로가 포함되었음을 나타내는 폐쇄성 증명이 없습니다. [호출·문자열 요약](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/analysis/ssm_callgraph_and_signatures.json)

특정 메서드의 outgoing call 목록만으로는 다음을 확정할 수 없습니다.

- 그 기능의 모든 caller를 조사했다.
- 다른 서비스·콜백·프로세스에서도 같은 책임을 수행하지 않는다.
- 동적 호출과 네이티브 경로가 모두 포함되었다.
- 모든 관련 값이 어떤 저장·전송 경로에서 소비되는지 확인했다.

따라서 질문에 제시된 `WatchingService`, `PolicyService`, `MeatGrinder`, `CameraWatchingService` 등을 포함해 **“미확인 경로가 없다”는 결론을 내릴 수 없습니다.** 여기서의 판정은 특정 추가 우회 지점을 확정했다는 뜻이 아니라, 전체 경로의 검토 완료를 입증할 자료가 없다는 뜻입니다.

또한 **애플리케이션의 반환값·비교 결과와 APK 자체의 서명 신원은 별개**입니다. 현재 patcher는 자체 서명키로 출력물을 서명하며 원본 서명 설치를 업데이트할 수 없다고 명시합니다. 특정 애플리케이션 내부 값이 일정해졌다는 사실을 설치된 패키지의 신원이나 외부 검증의 동등성으로 해석해서는 안 됩니다. [출력물 서명과 설치 제약](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/patcher/patch_ssm.py#L211-L232)

## 7. Universal 아키텍처에 대한 판단

### 현재 구현에도 동적 탐색은 일부 존재합니다

SSM의 네이티브 처리가 전부 고정 오프셋인 것은 아닙니다. `ELF` 구현에는 심볼 수집과 JNI 등록 후보를 찾는 로직이 있습니다. 이 점은 현재 설계의 출발점으로 인정해야 합니다.

다만 같은 구현에 특정 arm64 위치의 일치 검사와 별도의 고정 위치 변경이 함께 있으며, DEX 계획은 고정 오프셋 튜플입니다. Store도 고정 위치 중심의 계획을 사용합니다. 따라서 정확한 표현은 **“동적 탐색 요소가 포함된 특정 빌드용 구현”**입니다. [SSM ELF 탐색 및 계획](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/patcher/patch_ssm.py#L61-L120) · [Store 계획](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/store/patcher/patch_store.py#L37-L57)

### “모든 미래 버전 100% 자동”은 유효한 보장 범위가 아닙니다

오프셋과 난독화 이름을 제거해도 다음 버전에서 기능의 의미와 구조까지 유지된다는 보장은 없습니다. 기능이 분리·통합되거나, 호출 방식·정책 모델·서버 계약이 바뀌면 이전 버전의 대응 규칙으로 같은 의미를 식별하지 못할 수 있습니다.

설계 목표는 다음처럼 정의하는 것이 검증 가능합니다.

> 명시한 지원 범위에서 의미와 구조를 확인할 수 있는 입력은 자동 처리하고, 근거가 부족하거나 모호한 입력은 변경하지 않고 중단한다.

여기서 **자동 중단도 정상 결과**여야 합니다. 가장 비슷한 후보를 선택하는 방식으로 처리 성공률을 높이면 오탐 위험을 숨기게 됩니다.

### 일반적인 APK 분석·검증 도구에 필요한 구조

보안 우회용 타깃 규칙이나 변환 바이트를 제외하면, 다음 계층은 구체적인 설계 요구사항으로 제시할 수 있습니다.

| 계층 | 필요한 책임 | 중단 조건 |
|---|---|---|
| 입력 식별 | APK와 각 DEX·ELF의 실제 digest, 형식, ABI, 구성 수집 | 지원하지 않는 형식 또는 불완전한 입력 |
| 구조 해석 | DEX의 문자열·타입·필드·메서드 참조와 ELF 주소 관계를 파싱 | 범위 오류, 해석 불가능한 구조 |
| 의미 정규화 | 로컬 인덱스 대신 해석된 참조와 프로토타입을 사용 | 참조를 확정할 수 없음 |
| 후보 식별 | 문자열·외부 호출·프로토타입·제어 흐름 등 독립 근거를 교차 확인 | 후보 없음, 복수 후보, 근거 충돌 |
| 책임 목록 | 생산자·소비자·호출자·콜백·네이티브 연결의 검토 범위를 기록 | 필요한 연결이 미확인 |
| 변환 검증 | 허용된 변경 범위, 구조·타입·예외 처리·부수 효과 계약 확인 | 계약 불충족 |
| 출력 검증 | 실제 생성된 출력 전체와 예상 결과 비교, 플랫폼 검증 분리 | 예상 밖 변경 또는 검증 실패 |
| 증거 연결 | 입력 digest → 도구 revision → 계획 → 출력 digest → 검증 결과 연결 | 어느 단계의 정본인지 불명확 |

문자열 앵커나 명령어 마스킹은 **후보를 찾는 자료**로는 사용할 수 있지만, 그 자체를 의미의 증명으로 취급하면 안 됩니다. 특히 인덱스·레지스터 차이를 허용하는 과정에서 분기, 예외 처리, 실제 호출 관계까지 동일하다고 가정해서는 안 됩니다.

동적 인덱스 리졸버도 숫자를 새로 찾는 기능만으로는 충분하지 않습니다. **찾은 참조가 어느 DEX에 속하는지, 해당 참조의 타입·프로토타입이 무엇인지, 그것을 사용하는 명령이 유효한지**까지 연결되어야 합니다.

ELF/JNI 분석 역시 문자열이나 심볼 발견을 종료 조건으로 삼을 수 없습니다. 해당 ABI에서 주소가 어떤 영역을 가리키며, 등록 정보와 실행 대상이 어떻게 연결되는지 확인해야 합니다. 현재의 짧은 변경 창 목록만으로 함수 전체 실행 의미까지 검증했다고 주장할 수는 없습니다.

## 8. 요청한 7개 실패 유형과 2개 필수 점검

다음 두 조건은 다릅니다.

- 호출 종료 시 관측 상태가 목표 상태와 일치한다.
- 호출할 때마다 상태 설정 API를 반드시 실행한다.

첫 번째가 요구사항이라면 신뢰할 수 있는 상태 조회 후 동일 상태에서 반환하는 것은 유효한 멱등 처리일 수 있습니다. 두 번째를 요구한다면 동일 상태 반환 경로가 그 요구와 충돌합니다.

따라서 이 분기에 대한 판정에는 **조회 결과의 의미와 신뢰 범위, 목표 상태의 정의, 실패 상태의 처리 계약**이 필요합니다. 현재 자료에서 비교 분기가 남아 있다는 사실은 확인되지만, 그 사실만으로 조회가 잘못되었다거나 상태가 반드시 불일치한다고 결론 내릴 수는 없습니다.

### 1.4. 일반 CFG와 예외 CFG를 구분해야 합니다

같은 길이의 `nop` 치환은 뒤쪽 명령의 파일 위치를 유지합니다. 그러나 이것만으로 CFG 전체가 보존되는 것은 아닙니다.

- 기존 분기 명령과 그 목적지 위치가 유지될 수 있습니다.
- 제거된 호출이 만들던 상태 변경과 예외 발생 가능성은 달라집니다.
- 같은 `try_item` 범위를 유지해도 그 영역의 예외 발생 지점은 달라질 수 있습니다.
- handler가 남아 있다는 이유만으로 그 handler가 계속 도달 가능하거나, 반대로 도달 불가능해졌다고 단정할 수 없습니다.

현재 `u0`에 기록된 `try_item`은 3개입니다. 이 자료는 보호 구간의 위치를 보여주지만, 변경 후 모든 예외 간선을 검증한 결과를 제공하지는 않습니다. [메서드 헤더와 `try_item`](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/analysis/ssm_patched_and_core_methods.json#L8854)

이 판정은 공유 `validate_methods()`의 실제 구현 범위에 근거합니다. 이 함수는 명령어 폭, 일부 `move-result` 인접 조건, 레지스터 범위, try 구간 경계를 검사하지만, 타입 상태를 경로별로 전파하거나 CFG의 고정점 계산을 수행하지 않습니다. [공유 검증기](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/store/patcher/patch_store.py#L103-L162)

**레지스터 번호가 범위 안에 있다는 것과 그 레지스터의 타입이 해당 명령에 적합하다는 것은 별개의 조건**입니다. 마찬가지로 보호 구간의 양 끝이 명령 경계라는 사실만으로 예외 처리의 타입·제어 흐름이 유효하다고 결론 내릴 수 없습니다.

### 2.3. 분석 JSON의 원본 참조와 변경 후 명령열을 혼동하면 안 됩니다

메서드 분석 항목은 `orig_hex`, `patched_hex`, `changed`, `opcode`, `ref`를 함께 기록합니다. 변경된 항목에서도 `opcode`와 `ref`가 원본 명령을 설명하는 경우가 있습니다.

따라서 다음 두 방식은 정합성 검증이 되지 않습니다.

- 변경 후 호출 존재 여부를 원본 `ref`만으로 판단하기.
- 원본 명령 단위로 나뉜 항목을 변경 후의 독립적인 명령 경계 분석 결과로 간주하기.

변경 후 프로그램에 대한 판정에는 변경 후 바이트를 기준으로 해석한 명령 경계와 호출 관계가 필요합니다. [분석 항목의 구조](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/analysis/ssm_patched_and_core_methods.json)

### 2.4. `ssm_callgraph_and_signatures.json`은 완전한 caller/callee 대조표가 아닙니다

이 파일의 최상위 자료는 `patched_methods_summary`이고, 각 항목은 다음 정보를 갖습니다.

- 메서드와 DEX 식별 정보.
- 헤더·try 구간.
- 변경된 명령.
- 문자열·호출·필드 참조 목록.

반면 전체 정의 메서드를 대상으로 한 역방향 caller 목록, 호출 종류별 대상 해석 결과, 변경 전후 그래프의 분리된 간선 집합은 제공하지 않습니다. [호출·시그니처 요약 파일](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/analysis/ssm_callgraph_and_signatures.json)

여기서는 다음도 구분해야 합니다.

1. 명령에 기록된 메서드 참조.
2. 참조되는 메서드 선언.
3. 실제 호출 종류에 따라 선택될 수 있는 실행 대상.

선택된 메서드의 `unique_calls` 목록만으로 이 세 관계를 모두 검증했다고 할 수 없습니다. 따라서 **“42개 항목의 caller/callee 정합성 전수 통과”라는 결과는 현재 근거에서 나오지 않습니다.**

## 3. 고정 오프셋을 제외한 식별 유일성의 판정

### 3.1. 현재 자료로는 타깃별 유일성을 확정할 수 없습니다

유일성을 주장하려면 후보 집합과 식별 조건을 명시해야 합니다.

전체 후보 메서드 집합을 \(U\), 특정 역할의 식별 조건을 \(P\)라고 할 때 필요한 조건은 다음과 같습니다.

\[
\left|\{m \in U \mid P(m)\}\right| = 1
\]

현재 요약 자료의 42개 메서드는 선택된 부분집합입니다. 그 안에서 후보가 하나라는 사실이 확인되더라도, APK 전체의 정의 메서드 중에서도 하나라는 결론은 바로 나오지 않습니다. [분석 대상 메서드 집합](https://github.com/initguru/store-ssm-patcher/blob/1e0204fc54c16cee569c59f090d2275920ea12a4/ssm/analysis/ssm_callgraph_and_signatures.json)

따라서 이 자료만으로 각 타깃에 **“uniquely identified”**라는 판정을 붙인 매핑 표를 작성하면 근거보다 강한 주장이 됩니다.

### 3.2. 제안한 튜플의 각 요소는 서로 다른 한계를 가집니다

| 식별 요소 | 제공하는 근거 | 유일성 판단에서 남는 문제 |
|---|---|---|
| 외부 API 호출 시그니처 | 기능적 역할을 추정하는 근거 | 여러 wrapper·분기·서비스에서 같은 API를 사용할 수 있음 |
| 상수 문자열 리터럴 | 로그·UI·설정과 메서드의 연관성 | 중복, 제거, 변경 가능성이 있음 |
| 메서드 프로토타입 | 입력·출력 형태의 제약 | 같은 프로토타입의 메서드가 다수 존재할 수 있음 |
| 상대 명령어 오프셋 | 한 메서드 내부의 위치 관계 | 명령 삽입·삭제·컴파일 변화로 달라질 수 있음 |
| 요소의 결합 | 후보 수를 줄이는 교차 근거 | 전체 후보 집합에 대한 충돌 검사가 필요함 |

이 표는 유일성을 입증할 때 필요한 근거의 성격을 설명합니다. 특정 타깃의 자동 적용에 사용할 시그니처·리터럴·상대 위치 조합은 제공하지 않습니다.

### 3.3. 유일성과 의미 보존은 별도 판정입니다

전체 후보 집합에서 조건을 만족하는 메서드가 하나라도, 다음은 추가로 확인해야 합니다.

- 그 메서드가 기대한 책임 전체를 수행하는가.
- 같은 책임이 다른 메서드에도 분산되어 있는가.
- 호출자의 전제와 결과 소비자의 기대가 일치하는가.
- 비교 대상 버전에서 상태와 반환값의 의미가 유지되는가.

따라서 식별 결과에는 최소한 **유일함, 없음, 모호함, 근거 부족**을 구분해야 합니다. 상대 오프셋이나 이름을 제거했다는 사실만으로 버전 간 의미 동일성이 성립하지는 않습니다.
